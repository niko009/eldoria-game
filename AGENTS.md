# Eldoria — обязательные правила для AI-разработчиков

Эти правила действуют для разработки Eldoria через ChatGPT, Local Coder и другие AI-агенты. Не заменяют проектную архитектуру: сначала изучить `README.md`, `docs/HANDOFF_NEXT_CHAT.md` и относящиеся к задаче материалы `docs/`.

**Цель разработки:** перед добавлением больших новых систем добиваться законченной игры вдвоём: [docs/ELDORIA_COOP_MASTER_BACKLOG.md](docs/ELDORIA_COOP_MASTER_BACKLOG.md), [TASK-093–124](docs/TASK-093_124_COOPERATIVE_TASKS.md), [playtest protocol](docs/ELDORIA_COOP_PLAYTEST_PROTOCOL.md). Старые TASK-070–083 не считать полностью TODO или DONE без сверки с кодом. Сортировать готовые A-задачи по P0→P1, учитывать зависимости только внутри A; P2 DEFERRED — проектирование/спайки, не автоматическое внедрение. P0 не привязан к выбору новых мобов или UI-арта.

**Для автономной работы обязательно прочитать [docs/ELDORIA_DEVELOPMENT_QUEUES.md](docs/ELDORIA_DEVELOPMENT_QUEUES.md).** Задачи очереди A разрешены к разработке на отдельных feature-ветках; задачи очереди B требуют явного согласования конкретной модели/ассета/макета; B **никогда не блокирует A**. Подготовить варианты для B можно, интегрировать их без подтверждения нельзя. Это разрешение **не распространяется на release, production/БД, удаление данных или конфликтующие merge**. Не считать очередь исполняющейся в фоне без отдельного оркестратора.

## Перед изменениями
1. Уточнить цель задачи, проверить `git status --short --branch`, `git log -1 --oneline`, актуальность ветки и незакоммиченные изменения. Не затирать работу других агентов и пользователей.
2. Выбрать отдельную task/feature-ветку либо продолжить согласованную рабочую ветку. Не менять production ради проверки.
3. Для изменений геймплея проверить взаимодействие клиента и авторитетного сервера: нельзя доверять клиенту там, где требуется серверная валидация.
4. Формулировать критерии приёмки, включая Windows, Android и мультиплеер, когда они затронуты.

## Цикл разработки
1. Вносить минимальные согласованные изменения; не переписывать соседние системы без необходимости.
2. Проверять парсинг/сборку и релевантные тесты после каждого значимого изменения. Повторять после исправлений, не выдавать непроверенное за готовое.
3. Использовать Godot MCP для инспекции сцены, диагностики и визуальной проверки согласно `docs/GODOT_MCP.md`. MCP является дополнительным инструментом, **не заменой** автоматических тестов.
4. Для UI, графики, анимации, камер и эффектов делать реальный кадр из запущенной игры и анализировать результат; если графический рендер недоступен — явно указать ограничение.
5. Для изменений сетевого взаимодействия и игрового состояния запускать соответствующие двухклиентские/серверные тесты. Результат на одном локальном клиенте не подтверждает мультиплеер.
6. Для мобильных изменений дополнительно проверять touch/safe area/производительность. Linux screenshot не считается тестом на Android.
7. Зафиксировать выполненные команды, exit codes и выявленные ошибки. При отсутствии проверки статус «не проверено», а не PASS.

## Git, документация, релизы
- Коммитить только файлы своей задачи; до коммита посмотреть `git diff --check`, `git diff`, `git status`.
- Обновлять документацию и handoff при существенном изменении поведения или ограничений.
- **Не собирать и не публиковать релиз** после каждой задачи. Публикация Android APK, Windows-билда, сайта и production-деплой **только по прямой команде пользователя**.
- Не запускать опасные миграции, очистку ресурсов/сохранений или destructive Git-операции автоматически.
- Не называть задачу завершённой без доказательства работоспособности её критериев. Разделять: реализовано, протестировано, визуально проверено, требует ручной проверки.
- Финальный отчёт: ветка/коммит, что изменено, какие тесты реально пройдены, что осталось, наличие/отсутствие релиза.

Дополнительные инструкции: [Godot MCP](docs/GODOT_MCP.md), [проверки](docs/TESTING.md).
