# Eldoria: выпуск без ручных команд (через GitHub release-ветку)

## Статус

Реализованы **исходники и тесты**. Установка на production требует отдельного однократного административного действия. До установки таймера создание `release/eldoria-vX.Y.Z` **не запускает релиз**.

## Протокол

1. Разработка и полные тесты выполняются на feature-ветке.
2. ChatGPT создаёт в `niko009/eldoria-game` **новую** ветку строго `release/eldoria-vX.Y.Z` на проверенном commit SHA. Эта ветка — разрешение на публикацию, не создавайте её для экспериментальных изменений.
3. Серверный `eldoria-release-watcher.timer` раз в пять минут запускает `eldoria_release_watcher.py`. Он читает только ссылки на release-ветки фиксированного GitHub-репозитория. Переход к новой версии разрешается только при совпадении `latest.json` и `server.json`.
4. Контроллер передаёт конкретный SHA в `ELDORIA_EXPECTED_COMMIT` старому `/usr/local/bin/eldoria-release`. Скрипт проверяет SHA сразу после клонирования и до операций сборки. Скрипт выполняет прежние бэкапы, Android/Windows экспорт, проверку подписи, переключение Godot, проверку публичного APK и откат при ошибке.
5. Статус процесса атомарно сохраняется в `/var/lib/eldoria-release-watcher/state.json`, подробности — `journalctl -u eldoria-release-watcher.service` и в существующих каталогах release. При прерванном или ошибочном выпуске повторные попытки **блокируются до анализа**, чтобы не зациклить production-операции.

## Однократная активация (выполняется оператором с административным доступом)

**Важно:** до установки настроить GitHub ruleset для `release/eldoria-v*`: право создавать такие ветки только у доверенных участников. Иначе обладатель права push сможет инициировать production-сборку. Исключить из этого механизма релизы с миграциями SQL/API, для них нужен отдельный план.

На сервере получить проверенную копию репозитория. Инсталлятор сохраняет резервную копию действующего `/usr/local/bin/eldoria-release` и добавляет **только проверку SHA**, не заменяя скрипт из GitHub целиком. Для штатной работы релизов необходимо не удалять этот guard из установленного скрипта.

Из корня проверенной копии репозитория:

```bash
sudo bash scripts/install_eldoria_release_watcher.sh
systemctl list-timers eldoria-release-watcher.timer
sudo /usr/bin/python3 /usr/local/libexec/eldoria_release_watcher.py --dry-run
```

Важная деталь: `--dry-run` никогда не запускает релиз, не создаёт состояние и не меняет production. Сначала протестировать в режиме dry-run, затем создать новую release-ветку.

## Проверка и остановка

```bash
sudo journalctl -u eldoria-release-watcher.service -n 60 --no-pager
sudo cat /var/lib/eldoria-release-watcher/state.json
sudo systemctl disable --now eldoria-release-watcher.timer
```

При неудаче проанализировать журнал и проверить откат. **Не очищать статус `failed/started` без проверки базы, сайта и Godot**: это сознательная защита от повторного релиза.

## Ограничения

- Эта схема не зависит от GitHub Actions, работает без входящего HTTP-порта и новых ключей для GPT.
- Доверие основано на праве создавать строго именованные release-ветки. Репозиторий следует защищать настройками доступа и ruleset.
- Тесты/сборки на самом сервере заменять проверкой только имени ветки нельзя. Скрипт сборки — обязательный release gate.
- При остановке таймера или потере доступа к GitHub выпуск не произойдёт; версия сайта не должна считаться обновлённой без публичной проверки.
