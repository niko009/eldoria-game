## Правило разделения

Есть **две независимые очереди**. Агент всегда начинает с очереди **A (AUTO)**. Он может выполнить подготовительные технические, исследовательские и тестовые работы без пользователя, но не должен переходить в очередь **B (APPROVAL)** без отдельного одобрения **конкретного решения/ассета/макета**. Очередь B **не является зависимостью для A**: если A-01 завершена, агент сразу берёт следующую готовую A-задачу, а не ожидает выбора внешнего вида. Если задача требует выбора пользователя, выделить из неё подготовку в A, а выбор/внедрение — в B; не ставить весь roadmap на паузу.

**Статусы:** `TODO` → `IN_PROGRESS` → `TESTED` → `READY_FOR_REVIEW` → `DONE`; отдельно `BLOCKED_TECH` (указать причину). `TESTED` означает только перечисленные реальные проверки; ручной Android acceptance при отсутствии устройства — `NOT_VERIFIED`. `APPROVAL_REQUIRED` — состояние B, не разрешение на реализацию.

## Протокол автономной итерации

1. Читать `AGENTS.md`, этот файл и свежие `server.json`, `latest.json`, затем ветку с **последней подтверждённой кодовой базой**. Текущая `main` может отставать от релизной ветки. Проверить незакоммиченные изменения; **не работать в чужом dirty worktree**.
2. Выбрать первую `TODO` задачу из A, у которой нет технических зависимостей; для параллельной работы выделить отдельный worktree/feature branch. При `BLOCKED_TECH` подробно записать причину и взять следующую **независимую** A-задачу.
3. До кода записать AC и baseline; делать минимальный PR; запустить релевантные Godot import/headless, сетевые 2-client, PostgreSQL isolated, UI render и нужные mobile checks. Фактические результаты и нехватку устройства фиксировать в PR.
4. Коммитить и отправлять feature-ветку/PR с отчётом. Не вводить недоказанные `DONE`, не автосливать конфликтные изменения, не править рабочие ветки других агентов. После проверки переходить к следующей A-задаче.
5. Для B готовить **только подборку и preview**, помечать `APPROVAL_REQUIRED`; никакой выбор по умолчанию и никакого искусственного блокирования A. Одобрение — текст пользователя, привязанный к конкретной карточке/макету/версии файла.
6. **Не считать этот план запущенным фоновым процессом.** Нужен отдельный настроенный оркестратор/расписание для непрерывных итераций; этот документ задаёт порядок и границы полномочий, но сам ничего не исполняет.
